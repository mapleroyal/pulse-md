# Architecture

The product is intentionally one visible document surface per frameless window. A window may own multiple document sessions, but it mounts only the active session into its single editor surface. Minimal top and bottom chrome overlays the document; it must not create a native-looking toolbar/title bar, reserve permanent layout space, or introduce a sidebar.

This file is the source of truth for component and styling choices as well as process boundaries.

## Repository map

| Area        | Responsibility                                                                         |
| ----------- | -------------------------------------------------------------------------------------- |
| `src/`      | Sandboxed React renderer, CodeMirror editor, UI, and shared contracts                  |
| `electron/` | Electron main/preload processes, persistence, launch routing, and native integration   |
| `native/`   | Small platform helpers for macOS and Windows visual effects and native CLI integration |
| `scripts/`  | Native compilation, packaging, release checks, benchmarks, and repository screenshots  |
| `tests/`    | Electron end-to-end coverage and synthetic fixtures                                    |
| `build/`    | Checked-in icons and packaging resources, never signing credentials                    |
| `docs/`     | Build and CLI guidance plus representative repository screenshots                      |

Start at `src/App.tsx` for renderer composition, `electron/main.ts` for desktop
orchestration, `src/shared/contracts.ts` for the sandbox boundary, and
`electron-builder.yml` for the canonical packaged application. Run
`npm run check` before changing performance or packaging boundaries.

## Boundaries

- CodeMirror owns document text, selection, history, language parsing, decorations, search state, and the Markdown live/source presentation switch.
- Document identity is explicit and path-derived: recognized Markdown extensions use the Markdown parser and may enter rendered mode; every other path-backed UTF-8 file is plain text, remains in source mode, and may receive a lazily loaded filename-matched CodeMirror language parser. Pathless untitled, scratch, and standard-input documents default to Markdown. Save As adopts the destination extension's identity only after the write commits.
- Each renderer owns one primary mounted CodeMirror `EditorView`. Its active tab supplies the view's `EditorState`; hydrated inactive tabs retain their `EditorState` and lightweight presentation state without retaining hidden editor DOM trees. The scratch browser may lazily mount one additional read-only preview controller for its selected document; that controller is reused across selections, never created per result row, disables remote images and editing services, and is destroyed with the browser/workspace surface.
- Window bootstrap transfers the authoritative descriptor list plus only the active tab's document/session payload. Inactive initial tabs materialize one `EditorState` on first activation or one at a time during bounded idle work after both renderer and editor readiness. Idle hydration checks both already-loaded UTF-16 length and the current backing-file byte size; documents at least 8 MiB in either representation remain unmaterialized until explicit activation. The main process rechecks decoded length after the stable read to close file-growth races, and retains every hydration recipe and authoritative payload until the renderer acknowledges successful `EditorState` materialization. A deferred, failed, or stale hydration is isolated to that tab and never replaces the visible session.
- React owns lightweight application chrome and transient UI: tab/path metadata, the status overlay, search, and settings. Never mirror document text or CodeMirror state into React, and never rerender React for every editor transaction. High-frequency cursor, document-statistic, hover, and drag updates stay imperative or frame-batched at the narrowest boundary.
- The sandboxed preload exposes the narrow API in `src/shared/contracts.ts`. Renderer code has no Node.js access.
- The Electron main process owns the application-wide tab/window registry, native windows, native menus/dialogs, asynchronous files, settings persistence, launch routing, and close confirmation. The registry stores document identity, path/format/dirty metadata, window ownership, ordered tab IDs, and the active tab ID; it does not mirror live document text or receive per-keystroke updates.
- Keep core behavior on universal React, CodeMirror, Electron, and Node paths. Small platform adapters may translate behavior that Electron exposes differently—for example Windows session-end events, native helper transport details, or desktop-aware translucency—but must feed the same application transactions and storage primitives. Linux windows use Electron's ordinary opaque compositor. The macOS and Windows visual-effect helpers are deliberately narrow compositor adapters; do not move settings, theme resolution, renderer tinting, or window lifecycle policy into them.
- Link parsing and destination classification stay in the editor layer. Fragment activations remain inside CodeMirror, allowlisted external protocols cross the preload boundary to the OS, and relative local destinations are resolved against the source document by the main process. Following a linked Markdown/text document never silently replaces the source: the main-process registry first reuses the canonical file's eligible tab in the same window, then in another window, and otherwise creates a new tab. Cross-window reuse focuses that exact window and asks its renderer to activate the tab and resolve the fragment. Back and Forward retain explicit current-tab reloads for historical document entries whose original tab identity has since changed. Other local files use the platform opener. A canonical packaged scratch link is `pulse-md://scratch/<uuid>#fragment`; it encodes the stable public UUID rather than an editable filename, profile relationship, or private backing path. Every packaged build registers the `pulse-md` handler and uses the same packaged data channel, while checkout-scoped Development uses an unregistered `pulse-md-development` namespace; a scratch link is accepted only by its matching data channel. External URL launches enter the same validated single-instance launch-intent path and serialized singleton registry as profile launches, reusing a live scratch across windows or loading its saved Markdown before resolving the optional fragment. Copying a heading publishes a portable file URL or identity-specific scratch URL plus app-owned clipboard metadata; paste collapses that metadata to a fragment in the same document, relativizes it as `other-document.md#fragment` in another saved Pulse MD document, and retains the durable URL when no relative destination can be established. App-owned heading-link paste inserts the clipboard's portable plain-text form synchronously, tracks that exact range through later editor transactions, and upgrades only an unchanged range when asynchronous destination resolution completes. Generic Markdown paste prefers an explicit `text/markdown` clipboard representation; otherwise it inserts `text/plain` synchronously and lazily sanitizes and converts bounded `text/html` into Markdown. The same mapped-range and history rules upgrade only an untouched fallback, while code, link destinations, YAML front matter, tables, plain-text documents, and higher-priority app-owned clipboard formats retain their specialized behavior. The native Paste and Match Style command bypasses HTML conversion and inserts the clipboard's `text/plain` representation exactly. A user edit inside any pending fallback keeps the safe text; an editor-session replacement never erases already-inserted input.
- Filesystem path completion is split at the sandbox boundary. CodeMirror recognizes an unfinished Markdown destination or an unambiguous path from only the current bounded line and owns popup selection, keyboard, mouse, caret-relative positioning, and replacement semantics. Its popup presentation mirrors the shared shadcn Combobox/Command surface—popover tokens, dropdown radii and shadow, scroll containment, item spacing, icons, and one authoritative selected state—without moving transaction-frequency completion state into React or repeating file/folder helper labels. The selected row always retains the list's block inset after keyboard-driven scrolling, pointer movement updates CodeMirror's real selection rather than painting a competing hover state, and commands arriving during an accepted directory's asynchronous refresh are replayed in order when the next segment becomes active. The main process validates the source tab, resolves relative paths from its authoritative file path (plus home and absolute forms), streams a bounded directory scan while retaining only bounded candidates, and returns a bounded name/kind list; a newer request from the same window cancels superseded scan and symlink work, and directory access never enters the renderer. Directories sort before files, hidden entries require an authored dot prefix, and accepting a directory keeps completion active for the next segment. Tab accepts only while a completion is active or pending and otherwise retains the editor's ordinary list/indent behavior.
- Settings transfer uses native main-process file dialogs and bounded, versioned formats. An export without scratches may remain a JSON settings/profile envelope. Selecting scratches produces a ZIP with `manifest.json`, `settings.json`, one `profiles/<id>.json` entry per selected profile, and each scratch as exact raw bytes in `scratches/<portable-filename>.md`. The strict manifest maps each stable scratch UUID to its path, filename, nullable title, creation/modified/last-opened timestamps, and SHA-256 digest. ZIP import rejects oversized entries and totals, excessive entry counts or compression ratios, encryption, links, unsupported compression, unsafe or duplicate normalized paths, unlisted/mismatched entries, invalid UTF-8 JSON or scratch Markdown, schema violations, duplicate IDs, and hash mismatches before any state changes. Export snapshots every open scratch by UUID from its owning renderer using the tab's tracked BOM and line-ending format, while closed scratches are read as raw `Buffer` data from `ScratchStore`; exact encoded byte budgets are enforced before IPC cloning. Import performs a stable read and stages the complete transfer in the main process, returning only settings and resource summaries for preview/selection. Done applies selected profiles and standalone scratch snapshots transactionally with rollback before committing settings; Cancel discards the staged transfer. Scratch batch replacement publishes and syncs a strict transaction journal before moving any original, advances only after each filesystem phase is durable, and reconciles an interrupted transaction before exposing the store on the next launch. Open scratch UUID conflicts block replacement. An imported default-profile reference is retained when that profile is installed or selected for import and otherwise cleared. Ordinary path-backed documents are never included.
- CodeMirror owns spelling-error source ranges and their rendered underlines; never rely on Chromium's node-bound native markers because mounted editor DOM is disposable. The sandboxed preload synchronously classifies bounded, deduplicated word batches with Electron's session dictionary and supplies suggestions only on demand. Scan mounted source ranges in frame-bounded chunks, cache by exact word, and invalidate that cache when the platform dictionary initializes or changes. Dictionary mutation remains a validated main-process session operation.
- Packaged renderer assets are served only from the scoped `pulse-md://bundle` protocol. Privileged IPC accepts the owning window's main frame only when its location matches the renderer URL assigned at window creation; development-server URLs are local-only and are never honored by packaged builds.
- Appearance is resolved before the window is created. The native window background and blocking renderer bootstrap use the same persisted mode so dark launches never paint a light frame first. Background translucency defaults off. macOS windows are created with Electron's transparent-capable compositor because background alpha cannot be retrofitted reliably after construction. When translucency is enabled and the configured launch transition is disabled or has zero duration, renderer navigation starts, then the main process eagerly loads the small macOS bridge and atomically installs a WindowServer-aware Core Animation backdrop plus its theme-color tint before clearing the native backing and showing the window. The renderer's full-window surface is transparent in this settled state, so there is no later blur-only-to-tinted handoff when Chromium first paints. An opaque configuration never loads native blur code, and bridge failure keeps the themed native backing opaque. The backdrop and tint share a full-window container clipped to the native window's 10-point corner radius, switching to a square clip with AppKit's fullscreen mask, so composition and edge rendering have one boundary. The bridge prevents WindowServer from flattening that custom layer surface during Mission Control and Spaces transforms by applying the same high-word window tag AppKit uses for live resize, and reapplies it after AppKit clears it at the end of live resize. Private Core Animation classes and WindowServer functions are resolved at runtime.
- On Windows 11 22H2 and later, enabled translucency uses a small Windows Composition bridge: the modern alpha-only behavior of `DwmEnableBlurBehindWindow` lets a bottom-most desktop `BackdropBrush` sample the raw pixels behind the HWND, which feed a Direct2D Gaussian blur and an independent exact-alpha theme-color tint visual. The bridge does not use `HostBackdropBrush` or a system Acrylic material as its settled source, so Windows cannot impose a fixed blur, theme-dependent luminosity, or inactive-window fade; active and inactive windows retain the same Pulse-owned tint and radius. The saved 0–50 blur setting maps to Direct2D standard deviation at the same `0.25` calibration used by the macOS layer; zero bypasses the effect brush entirely for a genuinely clear, tint-only surface, while slider previews update brush properties without rebuilding the desktop target. Keep `BrowserWindow.transparent: false` so Windows Controls Overlay, native resizing, caption gestures, and Snap remain intact. Electron Acrylic is used only while the window is opaque to switch Aura's backing into its alpha-capable mode; the bridge immediately sets `DWMWA_SYSTEMBACKDROP_TYPE` to `DWMSBT_NONE`, enables DWM's alpha-aware blur-behind registration, and attaches its non-topmost target while Electron's material state remains internally active. Only then may the renderer backing become clear. On disable, failure, or Reduce Transparency, restore the themed opaque renderer backing first, detach the custom target, unregister blur-behind, and finally set Electron's material to `none`. A missing bridge, invalid HWND, or unsupported release stays safely opaque.
- A configured animated translucent launch reveal retains the themed opaque launch surface and starts after editor readiness, so animation setup does not delay focus or first input. The native layer pair already owns the final tint in every strategy. On macOS and Windows, `tint-blur` animates the native Gaussian radius from zero to its target while an opaque theme-colored renderer cover fades away; `tint` preloads the final native effect and transitions the renderer's same-color full-window surface to transparent; `cover` preloads the final native effect before fading its opaque cover. Duration, optional delay, and cubic-bezier easing are shared by the native and renderer animations. The transition defaults disabled. Reduce Motion settles an otherwise configured animation immediately after editor readiness; Reduce Transparency, an opaque configuration, or native-effect failure remains opaque. Failure to animate an otherwise usable native blur falls back to the preloaded `cover` strategy. Toolbar and status chrome must not stack another full-width tint; small readability surfaces may reuse the separately retained dynamic surface color. Do not use AppKit semantic vibrancy materials, CSS backdrop blur, whole-window alpha, or desktop capture in the product.

## UI rules

- Native window controls are always visible on macOS and Windows. Use precisely positioned native macOS traffic lights at the top left. On Windows, use Electron's Windows Controls Overlay for native minimize, maximize/restore, close, hover, and Snap affordances at the conventional top right; reserve that caption zone throughout wide, narrow, and zoomed layouts. Linux retains the simple red/yellow/green controls with intuitive close/minimize/maximize behavior. The persisted app-control set consists of one Back/Forward navigation unit, rendered/source mode, Find, Outline, Formatting Toolbar, and Settings; render it at the top right, immediately before the native caption controls on Windows, while retaining one internal settings schema. Window Chrome settings can enable the controls individually or all at once. Navigation renders both arrows only while at least one direction is available, and its divider disappears with the pair. On wide Windows layouts, reserve the current trailing app-control width in the tab strip before hover as well as after reveal, so a control can never replace a tab beneath a stationary pointer. At 520 effective CSS pixels and below on Windows, move the app-control cluster to the trailing edge of the shared formatting lane, reserve its exact current width from the formatting toolbar, and leave the tab row's leading edge undisturbed; at 420 pixels and below, collapse its document actions into the existing overflow while retaining Settings. The narrow control lane participates in the same editor clip, content padding, search/outline boundary, scrollbar inset, hover activation, and reading-position compensation as the formatting drawer even when formatting is disabled. When any control or contextual Markdown action is unavailable, the flex cluster, toolbar, and revealed tab strip reclaim its vacated slot; the minimum-width overflow menu exposes only currently enabled and applicable actions.
- Top chrome shares one fixed vertical centerline. At rest it shows the centered file path unless that item is disabled. Pointer hover over the top region replaces the path with solid, rounded, floating tabs; tabs visibility may pin that state always, while multiple tabs are open, or while the formatting bar is present. Drag entry also reveals a receiving window's tabs. Activating a tab minimally scrolls it fully into the tab-strip viewport once (and again if the strip DOM remounts); later wheel or direct scrolling remains user-owned. At the narrowest supported effective viewport, the active chip may shrink with the available strip rather than become impossible to reveal.
- On Windows, bare Alt temporarily replaces the ordinary 46-pixel top-chrome contents with a compact File/Edit/Format/View/Window/Help access strip; it never adds another layout lane or moves editor content. One renderer-owned Base UI menubar coordinates the top-level triggers and every dropdown so an open menu switches immediately through Left/Right navigation or sibling hover, including at renderer zoom. The main process remains the semantic authority: it freezes the current Electron application-menu tree into a per-window snapshot with opaque, single-session action tokens, and validated activation restores the pre-menu renderer focus before invoking the captured `MenuItem`. Keep the hidden Electron menu for accelerators and macOS behavior; never mix these renderer triggers with standalone native context-menu popups. Escape, a second bare Alt, outside interaction, window deactivation, or command activation restores the ordinary chrome. The native Windows caption controls remain reserved and interactive at the top right.
- Derive every tab surface from the resolved document background and foreground rather than theme-specific tab colors. The active tab uses the stronger foreground mix—darker than inactive tabs on light surfaces and lighter on dark surfaces—and profile-composer previews use the same tab selectors and tones. Its independently configurable indicator is one clipped overlay shared by live tabs and every profile preview: edge bars sit flush with the selected sides, corner wedges extend through the rounded boundary and expose one straight diagonal inner edge, and any edge/corner combination composes without changing tab layout. Resolve theme-accent, foreground-derived, focus-ring, and custom color sources from the live palette, with focus-ring as the default; dim palette-derived colors with window deactivation, while exact custom colors remain invariant unless their optional adaptive treatment is enabled.
- Empty top-region space is a native window-drag region. Tabs, their close buttons, app controls, and any custom window controls must be excluded from that drag region. Hovering tabs without a formatting toolbar expands the same lower chrome lane as that toolbar into an empty drag shelf, while leaving the tab row itself unchanged.
- Portaled menus, popovers, and every visible part of their interactive items must explicitly opt out of the frameless window drag region. Their pointer hit surfaces must match the complete painted item surface, including padding above and below its text row. A context menu supplies a full-window no-drag light-dismiss backdrop while open so every non-menu renderer click—including otherwise draggable blank chrome—dismisses it, and it also closes when the native window deactivates or resizes through native chrome. That backdrop stops accepting pointer input as soon as closing begins, allowing an immediate right-click elsewhere to replace the menu during its exit animation. The centered path owns its complete painted pointer surface above the otherwise invisible top-chrome activator, so entering that surface must explicitly latch the hover chrome before a navigation or formatting control is clicked. Path-backed tab menus expose path actions; scratch-tab menus instead expose metadata editing through the stable scratch UUID, while the Open Scratch preview retains its separate visible Edit button. Every visible app-control icon owns a shadcn context menu containing exactly one `Hide` action without changing primary click behavior; its popup opens inward from the pointer so it never intersects Windows' native caption-control rectangle. Either navigation arrow hides the shared pair, while hiding any other icon changes only that persisted control.
- The centered path and tab labels preserve and distinguish the filename. When a full path overflows, clip and feather its leading portion instead of computing a literal left ellipsis.
- Long, noninteractive notices such as full tab paths and disabled-profile guidance use the shared shadcn Popover positioning layer without adopting press-disclosure behavior. They open automatically on pointer hover or keyboard-visible focus, never move focus or latch on click, retain the ordinary tooltip colors, size to their natural text width, and wrap anywhere only when the collision-bounded available viewport requires it. The tab surface intent-loads this Popover so full-path help does not enter the launch-critical bundle.
- Bottom status chrome overlays the document and appears on hover unless pinned. It uses the document background with the conventional separator at its top, keeps its enabled editor details in the monospace font, and must not permanently displace the document.
- The primary CodeMirror scroller continues to own native Chromium scroll mechanics. Its incidental `tabindex=-1` focus after direct scrollbar interaction must not paint Chromium's square focus-visible outline; the editable content remains the meaningful focus surface. On Windows only, paint its WebKit scrollbar pseudos as a 10-pixel rail-less surface with hidden buttons, a quiet pill thumb, and stronger thumb hover; do not combine these rules with non-default `scrollbar-width` or `scrollbar-color`, which override the pseudo styling in Chromium. Its vertical track begins at `max(--window-chrome-height, --editor-clip-top)` and ends above `--editor-clip-bottom`, so ordinary top chrome, formatting/tab-drag drawers, and the visible status overlay can never cover the thumb. Other workspace scroll containers sit structurally below their own headers rather than compensating a full-window scroller.
- Electron page zoom scales the DOM surface, while native macOS and Windows controls retain their OS size. The preload reports every zoom-factor change so the main process can keep macOS controls and the Windows overlay height aligned with the DOM chrome's centerline; renderer geometry inversely scales the reserved Windows caption width for the same reason. Separately, Chromium visual zoom is enabled globally after renderer navigation for native pinch gestures; it magnifies and pans only the compositor viewport from 1× through 5×, never reflows the document or changes the persisted page-zoom factor.
- Use the checked-in `@/components/ui/*` shadcn components before creating application-specific controls.
- Document navigation uses a transient, searchable Outline popover anchored in top chrome. It must not reserve document space or become a permanent sidebar. A single lazily built heading index supplies the outline, heading shortcuts, active-section lookup, fragment-link resolution, and the fragment exposed by each live-preview heading's hover anchor; GitHub-compatible generated heading slugs keep ordinary Markdown fragment links portable. A heading anchor is a real interactive preview target aligned with the first visual row of a wrapped heading; its hit area bridges continuously to the heading text, and its dedicated app-owned context menu exposes only Open Link and Copy Link without moving the caret. The popover searches the complete index but mounts only a fixed, overscanned row window with height-preserving spacers; keyboard navigation and accessibility positions still address the full filtered result.
- The repository contains the complete shadcn registry generated with preset `b1VlIttI`; unused components are intentionally tree-shaken.
- Tailwind CSS 4 is the styling system for React UI. CodeMirror themes may use its extension CSS because editor decorations and gutters are not React components.
- Keep search and settings out of the launch-critical bundle when practical. The search overlay and its CodeMirror search support load together on the first Find intent; input and next/previous commands that arrive during that handoff stay in one bounded queue and are consumed exactly once by the mounted search owner. Open Scratch also remains deferred, but it presents no temporary dialog or input while loading: once visible, one dialog and one search-input DOM node remain mounted for the surface's entire lifetime. Its full-screen search/list/preview layout uses Base UI's non-popup Autocomplete state machine (the same `AriaCombobox` input/list engine without a selected form value) for text entry, while one app-owned cursor supplies wrapping Up/Down preview selection and retains only requests made against a stale asynchronous inventory in a local bounded queue. Rendered scratch previews create CodeMirror read-only from their first DOM commit and keep that auxiliary controller mounted across temporary empty search results. On macOS, a preview document replacement synchronously restores an already-active search input's native text registration, which Chromium can otherwise invalidate without changing `document.activeElement`. Deferred surfaces own their load failure locally: rejected module promises are not permanently cached, an actionable retry preserves any bounded handoff state, and an optional-surface failure never reaches the editor root. Regexp navigation replays from sparse canonical checkpoints (or a stable document/physical-line boundary) so backward navigation, counting, and replacement share one non-overlapping match phase; search-only announcements and scroll effects stay behind the same lazy boundary. Warm the settings chunk once the editor is ready and the renderer is idle so its first intentional opening is immediate.
- Settings is an explicit transaction: Done and the application save command commit the current draft, while Escape, the close button, and backdrop dismissal all discard it. Appearance changes preview immediately; on Windows the exclusive Settings session temporarily drives Electron's process-wide native theme source as well as the owning window's visual effect, remains authoritative across unrelated settings commits and additional window creation, and restores the committed source on every discard or abnormal session release. The dialog shell owns one scrollable body and one always-visible action/error footer so the commit decision and any failed save remain visible at the minimum supported window size. Transient editor recovery notices share one non-overlapping stack rather than independently competing with Search, Outline, or one another for fixed viewport coordinates; a failed recovery action updates its owning notice instead of escaping as an unhandled promise.
- Specialized settings workspaces remain lazy chunks. The launch-transition workspace is an opaque, renderer-only simulator so an already-translucent app window cannot contaminate its fixed 80%-translucent, 8-pixel-blur comparison surface.
- Treat persisted typography and persisted Electron page zoom as separate controls. Restore zoom before navigation so the first rendered frame uses the saved scale. If zoom later becomes document-only, isolate it at the editor surface rather than accumulating compensating transforms throughout application chrome.

## Tab and window sessions

- A new tab creates an untitled, empty, clean session. Open replaces the active tab only when that tab is this disposable blank; otherwise Open creates a new tab.
- Canonical file identity does not generally imply tab identity: ordinary Open may still create multiple independent tabs, and file watches, save acknowledgements, conflicts, and disposal remain scoped to each opaque tab ID. Link navigation is the deliberate exception and reuses one eligible canonical-file tab across the application before creating another.
- Same-window tab activation swaps retained `EditorState` objects into the one `EditorView`. Before the swap, activation reseeds the state's transaction-backed editor focus from that mounted view so every selection-sensitive preview makes one coherent source/render decision. Each inactive session retains CodeMirror's exact scroll snapshot plus physical offsets and a semantic anchor: activation seeds the shared scroller and gives CodeMirror its target before the next paint, then the semantic anchor corrects for geometry changes while the tab was inactive. Reordering changes the window's ordered tab IDs without moving document data.
- Tab dragging uses a visual ghost and an opaque tab ID. Never place a path or document content in the platform drag payload, and never mutate ownership while merely hovering.
- A non-final tab dragged beyond the deliberate tear-out threshold may create one non-owning provisional window keyed by that drag token. The main process follows the pointer imperatively while the source retains ownership; outside app-owned tab strips, the provisional surface becomes the native drop sink so another application cannot claim the opaque internal payload merely because it is underneath the cursor. The bootstrap and tab snapshots identify that temporary role, so the provisional renderer continues accepting the native drop but suppresses the ordinary receiving-window insertion slot and drag-over layout until promotion. Its renderer restores one serialized snapshot and explicitly reaches renderer readiness before release can commit the exact source revision and metadata baseline. Provisional windows durably suppress any configured launch reveal so a tear-out always retains its eagerly composed stable surface, including across promotion and native-theme notifications. On macOS, the same frame-paced pointer tracker samples native Escape state because AppKit's drag loop does not reliably deliver ordinary renderer input. Escape, an authenticated existing-window claim, save/external mutation, source closure, or any failed validation destroys the provisional window without removing the source session.
- On an accepted outside release, the source optimistically presents its neighboring tab while retaining the dragged `EditorState`. That retirement persists across intermediate registry snapshots and is acknowledged only after a compositor frame; ownership changes only after this presentation acknowledgement, destination readiness, and the exact-revision lease all agree. Failure settles the lease and restores the authoritative source snapshot.
- A valid cross-window drop is transactional: the source produces a versioned in-memory state snapshot, the destination restores it and acknowledges readiness, and the active source session takes a short read-only commit lease before acknowledging that exact revision. The main-process registry commits its new owner/order and explicitly settles the lease; only then may the source discard its session. Failure or cancellation leaves the source unchanged and restores source edit focus.
- Saving is transactional too: writes for a tab are serialized, the main process keeps the tab dirty after the atomic replacement, and only an acknowledgement for the exact saved renderer revision may mark it clean. Save As captures the destination baseline after the native dialog returns and rechecks stable bytes immediately before atomic replacement. The atomic handoff verifies the renamed inode, metadata, and exact bytes before adopting its baseline; on POSIX it refreshes the destination's permission bits after conflict approval, reapplies that commit-adjacent mode before the final file fsync and rename, and syncs the containing directory before reporting success. Windows uses the same universal write path without `chmod` or directory sync. An approved recreate after deletion retains the transaction's original mode. Directory watches are then re-established with a stat fingerprint check so no replacement can hide in the registration gap. Close, transfer, and disposable-tab replacement operations wait for, append around, or reject in-flight save transactions; a replacement transaction must also revalidate the renderer's current text and dirty state before discarding its candidate. Ordinary Open and file-drop reads hold a renderer-global, reference-counted read-only lease from the synchronized replacement decision through result acceptance, so an edit or active-tab switch cannot invalidate the main process's replacement predicate while asynchronous I/O is in flight.
- A non-final tab may be dropped outside existing tab strips to create a new window. The final tab may move only into another existing window; dropping it outside is invalid and must not destroy and recreate its source window.
- Closing a tab follows the document's dirty-save flow. Closing a window processes its tabs as individual closes, but does not dismantle the window until all required decisions and saves succeed. Cancelling leaves the remaining window and sessions intact.
- Application termination enters that same close transaction. It first quiesces new persistence mutations and CLI ingress, cancels stale read-only inventory work, then drains the captured managed-resource, CLI, settings, recent-document, window-state, and scratch-store mutation queues before calling Electron's final quit. macOS and Linux use Electron's ordinary application quit lifecycle; Windows additionally prevents `query-session-end` long enough to run the transaction for shutdown, restart, and logout. A session-end request never authorizes closing around unsaved or pending scratch state. Renderer recovery retains the original deferred hydration recipes and in-flight work instead of issuing duplicate reads; if a replacement renderer joins a silent background failure, the shared coordinator promotes it to exactly one interactive retry while the tab remains eligible.
- Tab backing is a first-class registry property, not a combination of incidental dirty/save booleans. `file` and ordinary `untitled` tabs retain normal prompting; `ephemeral` tabs discard silently; `scratch` tabs use private app-managed files and save atomically through the same revision-acknowledged transaction as ordinary documents. Scratch typing remains renderer-local and is size-aware debounced before crossing IPC. Per-tab generations coalesce auto-saves without suppressing an explicit save, canceled explicit copies re-arm normal auto-save, failed auto-saves retry with bounded exponential delay, and dirty scratch tabs must save before closing.
- A live profile window uses an immutable launch configuration whose scratch tabs contain explicit references to separately managed scratch UUIDs. The saved definition describes ordered typed tabs, an active tab, optional labels/colors, tabs visibility, a default initial editor mode, and optional per-tab mode overrides; its owning live window may replace that definition without hot-reconfiguring itself, so edits apply on the next launch. A different window may not edit an open profile, and no open profile may be deleted. "Update Current" capture preserves launched profile-local tab IDs, explicit scratch UUID references, and unchanged mode-inheritance choices; "Create from Tabs" deliberately records current effective tab modes and references to existing scratches. Profile JSON reads are bounded per file and in aggregate before decoding. File export creates a new destination unless CLI `--replace` is explicit. Deleting a profile removes only its definition and never deletes or exports referenced scratches; deleting the configured default clears and broadcasts that setting in the same rollback-capable mutation. Exactly one live window may own a profile and exactly one live tab may own a scratch UUID. Serialize profile mutations and launches so validation, reference checks, and window registration cannot race into duplicate scratch writers. Responsive profile-header actions collapse to square, centered icon buttons when their labels hide; disabled-profile guidance uses the shared automatic long-text Popover at its natural collision-bounded width, and its disabled action remains keyboard focusable with the same persistent assistive description shared by Delete.
- `ScratchStore` owns standalone scratch persistence: every document is a literal Markdown file, while a strict sidecar catalog records its stable UUID, editable portable filename, optional title, creation time, and last-opened time. The UUID remains the resource identity across filename/title changes and profile references; profile-local tab IDs are never storage identities. Settings provides scratch creation, rename/title editing, search/preview, sorting, and deletion over this store. Entering scratch metadata management records whether it came from Settings, Open Scratch, or an editor tab; Back returns to that exact surface, retaining the Open Scratch query and selection when applicable, rather than routing every exit through Settings. Scratch content search streams stable files through bounded UTF-8 chunks, performs matching inside the store without retaining whole decoded copies, and cooperatively abandons superseded per-window query generations; read-only inventory work never serializes ahead of managed mutations. Scratch export and deletion require the UUID's single live tab to be closed so renderer debounce cannot make storage stale, and deletion is rejected while any profile references that UUID. Scratch inventories explicitly report whether profile references were available; a profile-store failure must not masquerade as an authoritative empty reference set or turn an already-successful metadata mutation into a failure. File export must atomically publish a fully written new destination without an overwrite race and cannot target app-managed scratch storage lexically or through a symlink.
- Persisted global settings and effective per-window settings are distinct values across the preload boundary. CLI/profile presentation overrides affect their owning window without leaking into the settings file; opening Settings still edits the persisted base values. The preload retains each renderer's latest persisted baseline, and the main process rebases only fields changed from that baseline onto the current global settings inside the serialized commit, so independently issued pre-broadcast changes cannot overwrite one another. A missing settings file is a clean default state; an unreadable, invalid, or schema-incompatible existing file is instead a startup recovery transaction. Retry never mutates it, Quit leaves it untouched, and an explicit reset first preserves the exact original under a unique recovery name before defaults become writable authority.
- `Cmd/Ctrl+T` creates a tab. `Cmd/Ctrl+W` closes the active tab, or closes the window when it contains only that tab. On macOS, Command+1 through Command+9 select the corresponding first nine tabs; Control+1 through Control+0 select the first ten tabs on every platform. Control+Tab / Control+Shift+Tab cycle. Horizontal wheel gestures retain native scrolling across the full moving surface of an overflowing tab strip or formatting toolbar, including when an overflow control moves under the pointer; vertical mouse-wheel gestures scroll either surface horizontally according to the configured down-to-right or down-to-left direction. Elsewhere in top chrome, wheel gestures route to overflowing tabs; an overflowing formatting toolbar retains ownership over gestures on its own surface. The window close control closes the whole window.

## Launch routing

- Run one primary application process while any window exists. Queue startup requests until application readiness, and route Finder/file-association launches and CLI commands through the same main-process tab/window registry rather than directly selecting an existing renderer.
- Because the native window is visible while Chromium bootstraps, the main process must retain native menu commands per window until the editor-ready handshake, then deliver them in order. The queue belongs before `webContents.send`: preload does not yet exist during the earliest visible interval and cannot make an early send reliable. Capture pre-readiness `Cmd/Ctrl+T` at `webContents`' input boundary and prevent that input from also activating the application-menu accelerator; preload forwards the same shortcut only as a fallback for hosts that inject a DOM event without native input. Both paths enter the one main-process queue, and after readiness the renderer remains the sole keyboard-policy owner.
- Keep the two external transports intentionally separate. Finder, file associations, and direct bundle launches use Electron's structured single-instance handoff and remain strict `new-window` intents with optional file paths. The native CLI helper uses a versioned, same-user local socket/named pipe because terminal output, stdin, readiness acknowledgement, and `--wait` require a bidirectional lifetime. Packaged `pmd` and checkout-development `pmd-dev` have distinct compiled launch targets and endpoint identities; a helper must never fall through to the other identity's process or user data.
- The helper sends only bounded UTF-8 metadata plus an explicit-length stdin stream; it never puts document contents in argv or Electron single-instance metadata. POSIX runtime directories and sockets must be private to the current uid. Windows derives its pipe name from a stable digest of the user's profile path (not the collision-prone username) and the native client additionally verifies the server process SID. A seekable nonempty regular-file stdin source is streamed directly by the helper; pipes, special zero-size files, and unknown-length streams are spooled to private temporary storage so large input is never buffered in the main process and the protocol can retain its explicit length.
- Spool decoding is performed by the document utility from its private file path rather than transferring the complete byte stream through the main process. Scratch stdout validates the closed scratch in a bounded first pass, then uses a versioned stream of bounded, UTF-8-safe content frames followed by one terminal response, so malformed data never produces partial stdout, output is not limited by a single protocol frame, and leading byte-order marks remain document data.
- A Finder/direct `new-window` intent always creates a new window. File > Open Recent is deliberately separate: a normalized, bounded app-owned MRU supplies the same explicit menu on every platform, while macOS and Windows also receive best-effort native recent-document mirroring. Selecting a recent item retains the invoking/focused eligible window even while it is booting or completing another tab mutation, serializes with that mutation, and inserts a tab there; only the active disposable blank may be replaced. A new window is created only when no eligible document window exists. The MRU is atomically persisted and flushed through the normal quit transaction. A CLI open also creates a new window by default; only explicit `--reuse-window` may append tabs to the most recently focused usable window. Named profiles and scratch IDs have explicit singleton focus semantics rather than silently reusing unrelated windows.
- CLI success is a readiness contract, not merely successful process creation. Show or restore the exact target window with `BrowserWindow.show()`, then wait until the renderer confirms the requested tab is active and CodeMirror owns keyboard focus. New-window bootstrap, reuse injection, and existing profile/scratch focus all require an acknowledgement before the helper returns or enters its `--wait` state. Do not use application-wide focus calls that can raise sibling windows.
- Bare `pmd --profile` and `pmd profile open`, File > Window Profiles > Launch Profile, and the Settings launcher share one lazily loaded searchable renderer picker. A CLI picker request uses an eligible existing document window or a fresh disposable host, never a renderer occupied by another modal or mutation; cancellation completes without launching, while a selection re-enters the serialized singleton profile-launch path and satisfies the same editor-focus and `--wait` readiness contracts as a direct profile ID.
- `--wait` tracks the opaque IDs of exactly the tabs created or selected by that request and completes only after all are disposed, even if tabs move between windows. Client disconnect removes the tracker without changing document state.
- Metadata and storage-management commands never create a document window. Read-only metadata, help/version, usage errors, and non-window CLI-bootstrap commands run before Chromium application initialization; a CLI-only cold bootstrap exits after its queued request and terminal response complete when no window remains. Platform activation remains registered during that deferred initialization, promotes the process to ordinary application startup, and opens a document window once initialization completes. The native helper captures active-window bounds only for commands whose placement can use them.
- Missing CLI file leaves are clean, path-bound documents and are created only by the ordinary atomic Save transaction. Standard input becomes a dirty untitled document with an explicit empty baseline. Line/column targeting is one-based at the CLI boundary and clamped by the editor controller after session creation.
- CLI source order is tab order. Window mode is the default, while numbered per-tab mode and cursor overrides travel with each bootstrap tab through both cold-window and reuse-window paths. Construct the active editor directly in its resolved tab mode so per-tab configuration never requires a launch-time reconfiguration or wrong-mode first paint.
- Keep request routing separate from platform placement. On macOS, Finder/direct launch windows are centered in the work area of the display under the pointer. The native CLI helper captures the active system window bounds before contacting or launching the app, so a new CLI window defaults to that window's display; an explicit `--mouse-monitor` flag and an unavailable active-window capture use the pointer display. Native window creation lets the OS place windows on the current Space. Electron exposes no active-Space assignment API, so any stronger guarantee belongs in a future platform adapter without changing tab identity or document ownership.

## Performance rules

- Package and benchmark release builds, not the Vite development server.
- Keep the active editor eager. Load top chrome through a retryable deferred
  boundary as soon as bootstrap supplies active-tab state; it overlays fixed
  document geometry, so the split must not move or resize the editor. Defer
  other nonessential UI, inactive documents, and inactive editor state.
- Before constructing the first `EditorView`, wait only for the configured regular and monospace faces that can render the initial document. The bounded glyph sample seeds restored viewport and main-selection positions before scanning broader beginning/middle/end segments, so the code-point cap cannot omit the initial anchor's Unicode face. This prevents fallback-font first paint and stale wrapping geometry without loading the font catalog; later `FontFaceSet` completions must force a full CodeMirror content-geometry refresh.
- A mode switch reconfigures one `EditorView` and then fully refreshes its content geometry because live/source typography can wrap differently. Its semantic viewport anchor retains the active selection endpoint's association across the reconfiguration and rejects CodeMirror's all-zero hidden-geometry sentinel. Do not mount synchronized live/source editors.
- Disabling line wrapping keeps CodeMirror's intrinsic widest-line track so ordinary text and horizontal rules retain stable document-wide horizontal geometry. Rendered block surfaces—including YAML front matter, quotes/callouts, code, tables, display math, Mermaid, sanitized HTML, and images—must instead cap themselves to the visible document lane and own any narrower horizontal overflow; a centered preview must never center against the longest unwrapped source line.
- Calibrate CodeMirror's document-wide base text geometry from a plain editor line and refresh that calibration only with deliberate content-geometry changes. A syntax-decorated line entering the virtualized viewport must never redefine the estimates for every unmeasured document gap.
- Inline and non-layout live-preview decorations are limited to visible ranges. Layout-affecting block replacements—including callout headers, display math, Mermaid fences, and sanitized HTML blocks—retain complete, directly provided decoration sets in CodeMirror state before viewport calculation; their membership must never depend on `view.viewport`. CodeMirror still virtualizes the corresponding widget DOM, so complete height structure does not mount or render every offscreen widget. Typography, wrapping, or content-width changes invalidate optional-block height caches before the full geometry refresh in every mounted editor controller, including the scratch preview; typography and completed font loads also advance Mermaid's render generation so SVG layout cannot retain fallback metrics. Viewport-fragmentable block wrappers must not own leading vertical geometry; attach it to semantic state-backed lines or widgets. Preserve the established heading-marker and table geometry invariants when extending Markdown rendering.
- A plain, unmodified pointer down on an opaque rendered preview is inert: it neither moves the CodeMirror selection nor reveals source until pointer up. A true click then selects the preview's declared semantic source (math declares its body without delimiters), while movement beyond the shared drag threshold cancels click activation for atomic previews. Callouts and sanitized block HTML alone retain a native rendered-text selection; clamp that DOM selection to its originating preview so it copies rendered content without source markers or neighboring text. A drag that starts in ordinary source remains CodeMirror-owned; freeze layout-changing decorations through pointer up, then map an endpoint inside a preview to its indicated source edge before refreshing. The first opaque unit entered owns its nested DOM for that source-origin gesture, and its live range moves only between complete semantic edges rather than partial source inside the unit. When a pointer physically hits a mounted source row beside a tall replacement, its DOM caret position within that row outranks a `posAtCoords` result inside the replacement's hidden source. The deepest rendered callout still owns every nested preview for a rendered-origin gesture; explicit controls and modifier-based link navigation keep their own behavior, source-mapped constructs retain precise pointer mapping, and keyboard selection or arrow motion never enters this pointer-only resolver. Whole-line display math consumes one adjacent line break at each replacement boundary, as block HTML does, so its preview creates no ghost rows while retaining authored blank lines. Ordinary fenced-code content remains position-precise, while a press on either delimiter row places the caret at that source line's end. A content-origin drag that enters a synthetic fence boundary row maps to the adjacent rendered-content edge, never to overlapping hidden delimiter or language anchors. The code-block extension owns every code row's structural classes—including first and last boundary rows—so numbered content and quote prefixes retain one lane when an enclosing callout reveals raw source.
- Every selection-sensitive live-preview subsystem consumes that transaction-backed focus signal rather than independently reading DOM focus. The app-owned editor context menu retains that signal while its accessible popup owns DOM focus, then restores editor focus before releasing it. If CodeMirror drops a queued focus effect behind another transaction, live preview reconciles it through one shared refresh, deferred while pointer selection or composition freezes layout.
- Selection geometry is one deterministic CodeMirror layer derived only from mounted ordinary lines and rendered table rows. Map each mounted DOM interval to source exactly once, sort it, and sweep it against sorted selection ranges; never measure one document-wide DOM range across replaced table DOM. Ordinary rectangles are clipped to their mounted line and text lane, then every intermediate visual row fills the lane and vertically adjacent full-lane rectangles merge into one body, leaving only the first and last visual rows partial. Vertically adjacent ordinary fragments divide their intervening whitespace at a shared midpoint; never synthesize a full-lane bridge where there is no intermediate visual row. Table rectangles remain independently clipped to their row/cell and visible horizontal table viewport, and selected newline boundaries receive a narrow row-local cue. Repeat the same fill on source-backed selected text so opaque semantic surfaces cannot cover the layer. Refresh geometry from CodeMirror geometry/viewport changes, captured bounded-preview scrolling, and coalesced outer horizontal scrolling without installing document-wide mutation or resize observers.
- Plan each physical live-preview list prefix once across indentation, alternating list/quote containers, markers, and marker whitespace. Keep every ordinary prefix segment source-backed in an ordered fixed-width lane and cancel the aggregate lane with the line's text indent, so authored offsets retain exact caret and pointer positions without changing the semantic content column; an authored continuation inherits that column from its deepest owning item. Paint semantic bullets over their authored source. A task checkbox is the deliberate exception: replace its complete visual prefix and publish the same full-document range through `EditorView.atomicRanges`, while an ordered task's authored ordered marker remains source-backed.
- Treat CommonMark/GFM's marker-relative content column as the invariant for list depth: task checkboxes are item content, post-marker whitespace contributes one to four columns, and tabs are measured at physical four-column stops from the complete line/container prefix. Generate valid indentation automatically: use spaces when no local pattern exists (two for conventional bullet/task parents), adapt to wider ordered markers, and reuse a nearby authored child-tab pattern when one exists. Sibling Enter and empty-item lifting preserve the authored prefix instead of normalizing existing source. Enter at the content start of a split item lifts that retained content by exactly one list level; Shift+Enter exits list indentation directly while retaining an enclosing blockquote container. A loose-list parse may affect rendering, but it must not cause Enter to manufacture blank separators.
- A rendered table's state-backed wrapper has higher facet precedence than an enclosing callout/quote wrapper, so the table remains nested at the callout body's width even though its local wrapper rank is narrower. When the enclosing callout intentionally reveals raw source, the overlapping table wrapper, atomic ranges, structural decorations, and table-specific handlers all defer together; literal pipes then accept ordinary pointer and arrow-key caret movement, and the rendered nested table restores when source editing leaves the callout.
- Full-document heading, callout/quote, code-block, link-reference, and enabled layout-replacement indexes share a complete syntax tree cached by CodeMirror's immutable document value. Non-layout semantic indexing remains demand-driven, while layout-affecting indexes seed complete range sets synchronously so offscreen structure never changes height while scrolling. Persistent range indexes and their direct decoration sets map across block-shape-preserving edits and refresh only affected top-level syntax; selection moves that touch no indexed block must reuse the existing complete decoration state. Fenced-code and display-math delimiter lines are deliberate rare full-index invalidations because symmetric delimiters can re-pair distant siblings. The quote index likewise rebuilds when a changed line neighborhood's quote-content blankness or parsed block/container structure changes, because CommonMark lazy continuations can alter distant grouping without changing a literal quote prefix. A partial viewport-tree publication for the same immutable document must never trigger another full semantic scan. Never rebuild the outline index on ordinary transactions or mirror it continuously into React while the popover is closed.
- Documents at least 16 MiB encoded or 8 million UTF-16 code units move UTF-8 decode/normalize/hash and encode/hash work to one lazily started Electron utility process. Heavyweight requests enter that serial utility one at a time so concurrent callers cannot accumulate cloned IPC payloads; smaller documents stay in-process to avoid transfer/startup overhead. File reads require stable handle-before/handle-after/path fingerprints, save conflict checks always compare stable bytes rather than trusting unchanged metadata, and actual watch events force a content read.
- Word counts remain incremental for ordinary edits. Initial documents at least 1 MiB and edits affecting more than 256 KiB publish a pending status and finish through bounded idle slices; the scanner carries Unicode word state across chunks without materializing the whole document.
- Only the default Inter and Cascadia faces enter the initial CSS closure. Other included families, the formatting toolbar, and optional live-preview implementations load on demand; optional math and Mermaid engines retain their inner lazy imports. Cached rendered HTML and Mermaid fragments use weighted memory budgets with count caps as secondary guards, and a single oversize fragment is never retained. `npm run bundle:check` follows the HTML/CSS dependency graph and enforces initial JavaScript, CSS, font, closure, total-output, and WOFF2-only budgets.
- The CodeMirror language-description catalog is also outside the launch-critical bundle. Load it once during an idle turn after the first editor is ready, then reconfigure active and subsequently activated sessions from the same universal controller path. Markdown uses it for fenced code; plain files use the same catalog for lazily loaded top-level syntax support matched by filename.
- Closed-document history retains lightweight document identity and originating-window ownership in the main process. A renderer-confirmed tab close also records its last physical/semantic viewport; the history never retains document text or editor history. Reopening reloads the document and returns it to that window while it survives, restoring a recorded viewport against the fresh content; a new window is reserved for a closed origin. Inactive tabs retain data/`EditorState`, never hidden editor DOM trees or one renderer process per tab.
- No network request belongs on the startup path.
- The optional macOS Keep Ready in Background setting registers the installed main app as a `mainAppService` login item. A login-item launch with no file, URL, CLI, or queued activation work initializes the singleton without a window under the accessory activation policy. With the setting enabled, Command-Q enters the same serialized save/cancel window-close transaction as application termination, then hides and deactivates the app under the accessory policy while retaining the Electron main process; Option-Command-Q and OS/programmatic quit requests always complete the real quiesce-and-terminate transaction. A file, URL, CLI, second-instance, or activation request arriving during the close transaction is queued and restored after a cancellation or successful background close. The first later window request restores the regular activation policy, unhides the app, and constructs Chromium UI. The setting is disabled by default, isolated test/benchmark profiles never mutate global login items, and interactive recovery always restores foreground activation.

### Historical launch benchmark record

The measurements below are machine-specific evidence from development, not a
performance guarantee for other hardware or releases.

On 2026-07-16, 20-run cold-launch measurements of the installed, signed macOS app via `/usr/bin/open -n`, using a fresh isolated profile per run and the benchmark-only inspection flags, produced these elapsed times from process launch (median / p95):

| Document                                  | DevTools endpoint | Editor visible | Editor focused | Input accepted |
| ----------------------------------------- | ----------------: | -------------: | -------------: | -------------: |
| Empty                                     |      297 / 337 ms |   389 / 443 ms |   400 / 455 ms |   408 / 464 ms |
| Mixed syntax, 212,361 bytes / 6,630 lines |      308 / 327 ms |   437 / 466 ms |   452 / 478 ms |   462 / 497 ms |

The same optimization pass reduced direct packaged-executable median input acceptance from approximately 519 to 453 ms empty and 544 to 475 ms heavy. The heavy-document 500 ms p95 target is therefore realistic and met on this machine; a reliable 300 ms cold empty-document target was not achievable through renderer micro-optimization while Electron's inspectable endpoint alone takes about 297 ms median. Reaching it would probably require a broader startup architecture such as a persistent helper or native shell.

On 2026-07-19, a benchmark-only launch override compared opaque startup, the current deferred no-transition path, and native blur installed before the first `show()` call. One signed package ran three warm-up triads followed by 20 measured triads in balanced interleaved order, with a fresh profile per process and transitions disabled. Results are median / p95:

| Mode     |   Native setup | Show-to-clear interval | Editor visible | Editor focused | Input accepted |
| -------- | -------------: | ---------------------: | -------------: | -------------: | -------------: |
| Opaque   | 0.04 / 0.04 ms |                    n/a |   504 / 534 ms |   516 / 549 ms |   526 / 559 ms |
| Deferred | 1.42 / 1.62 ms |           132 / 211 ms |   499 / 548 ms |   510 / 562 ms |   520 / 572 ms |
| Eager    | 1.33 / 1.47 ms |               0 / 0 ms |   519 / 554 ms |   529 / 564 ms |   538 / 580 ms |

All 20 eager runs completed native setup before the window's `show` event, by 73-153 ms (129 ms median). Against the opaque run from the same triad, eager input acceptance had a +8.73 ms paired median, but individual deltas ranged from -61 to +81 ms; native setup itself was consistently about 1.3 ms. This establishes the show-to-clear benefit and bounds the observed startup cost, but compositor-frame appearance still requires visual inspection outside Chromium capture.

On 2026-07-21, after moving the settled full-window tint into the same native layer transaction as the backdrop, a signed candidate ran three warm-up triads and 20 measured balanced triads. Native eager setup remained 1.28 / 1.49 ms median / p95, versus 0.05 / 0.06 ms for opaque bookkeeping. Eager input acceptance was 393.76 / 412.16 ms, compared with 390.46 / 411.10 ms opaque; the paired median delta was +4.67 ms. The complete native effect was ready 46-74 ms before `show()` (67 ms median), and the WindowServer compositor test separately confirmed that the native tint changes captured pixels while the renderer's full-window shell remains transparent. Thus the stable first surface adds no material startup regression and does not require delaying the window until Chromium's `ready-to-show` event.

Use the eager path for production translucency when no launch animation is configured; keep the themed native background visible while Chromium loads when the effect is opaque or an animated reveal is configured. Preserve all three benchmark modes, the launch marks, and `scripts/benchmark-launch.mjs` for diagnosis. Do not construct CodeMirror eagerly in the preload: that experiment started it about 100 ms sooner but caused repeatable viewport-anchor regressions in long documents; font preloading and forced measurement did not correct them.
